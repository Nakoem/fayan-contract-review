## 0. 背景与目标

把法眼的内核（审查链路 / 提示词 / 规则 / 六段式报告 / 三维评分）包装成面向个人的单文件产品：**粘贴或上传合同 → 90 秒内出带法条依据的风险报告**。

MVP 只回答一个问题：**"有人愿意用这个审合同吗？"** 主体范围限定在「审」；V1.5 补本机「最近审查 + 合同台账 / 到期提醒」；不做文书、多案件、完整企业台账。

---

## 1. 范围

### 做

- 单文件 `dist/index.html`，双击可用，零外链、零 CDN、零外部字体
- 粘贴文本 / 上传文字层 PDF、DOCX、TXT / 载入 6 份内置示例合同
- 6 类合同：房屋租赁 / 劳动 / 买卖 / 服务 / 合作 / 借款
- 5 步审查流水线（抽取 → 法条 → 评估 → 复核 → 报告）
- 审查视角：审查前按合同角色选择（中立 / 双方角色），视角进入评估提示词、复核与报告
- 六段式报告 + 三维评分 + 风险条款正文高亮 + 点条目跳转
- 风险条目挂载本地检索到的法条参考片段，报告内可展开
- 规则 JSON 数据化（111 条），条款库页面复用同一数组
- 服务商预设：DashScope（默认）/ DeepSeek
- API Key 本地保存、脱敏开关（默认开启）
- 导出 `.docx` + 浏览器打印
- 设置持久化；当前审查结果单槽持久化（刷新恢复）
- 案头 + 最近审查历史：审查完成自动入库，支持搜索、打开报告、删除、清空；全部在本机 IndexedDB
- 合同台账 + 到期提醒：审查结果一键入台账（本地自动带入对方 / 金额 / 日期 / 付款节点），或手动新增；单到期日 + 单下次付款日；案头汇总 30 天内待办；支持搜索、状态筛选、CSV / `.ics` 导出

### 不做（明确排除）

- 扫描版 PDF OCR、旧版 `.doc` 解析、文书起草、多案件 / 完整企业台账、完整台账字段自动抽取（V1.5 只在加入台账时本地识别常用字段）、多付款节点 / 循环提醒 / 自动续签、向量检索、Ollama 预设、Lucide 图标
- 规则编辑 UI 已在 V1.5 补上；立场切换 UI 已在 V1.5 以「按合同角色选择审查视角」补上（见 §11 V1.5 第四块）
- 自定义合同类型

### 与 PRD 的差异（2026-11-19 定稿）

| # | PRD | 实际决定 | 原因 |
|---|---|---|---|
| 1 | 三个预设：DeepSeek / 智谱 / Ollama | DashScope（默认）+ DeepSeek，**不做 Ollama，智谱移出 MVP** | 用户拍板；智谱浏览器 CORS 不可用，直接移除 |
| 2 | "五段式报告" | 沿用 `prompts.py:92-142` 的**六段式**模板 | 手上真实的模板就是六段（概览/高/中/低/优先级/签约建议），不另造 |
| 3 | 立场切换 P1 | MVP 无 UI，规则 schema 保留 `stance`；V1.5 补为「审查前按合同角色选择视角」 | 符合 P1 定位；视角按合同角色建模，避免甲方/乙方在不同合同里含义错位 |
| 4 | 条款高亮 P1 | MVP 做**基础版**（原文查找 + 标色 + 滚动定位） | 是审查台核心体验，成本低 |
| 5 | 条款库 / 规则库分层 | 条款库直接由 `RULES` 渲染 | 一鱼两吃，不维护两份内容 |
| 6 | 历史记录 / 台账第二阶段 | 本机「最近审查」+ 单机合同台账 + 30 天到期提醒；不做多案件 / 完整企业台账 | 先解决“审过的合同找不到”和“到期漏看”；成本低于完整台账 |

### 模块约定（关键）

- 所有 src 逻辑文件采用 **IIFE + `globalThis.WB` 命名空间**，不写 `import/export`：
  ```js
  (function (root) { const WB = root.WB = root.WB || {}; WB.RULES = [...]; })(globalThis);
  ```
- 浏览器开发态：`index.html` 用 `<script src="...">` 按顺序加载
- 构建态：`build.py` 按同一顺序把脚本内联进 `<script>`
- Node 脚本：用 `await import()` 按顺序加载同批文件，共享 `globalThis.WB`，无需打包器
- **DOM 依赖隔离**：`prompts.js` / `llm.js` / `pipeline.js` / `data/*` 不碰 `document`/`window`，保证 Node 可跑

### 构建规则

- `build.py` 读取仓库根目录 `sample_*.txt` 与 `knowledge/*.json`（单一数据源，不复制内容）
- 构建时先**生成** `src/data/samples.js` / `src/data/knowledge.js`（文件头标注 `AUTO-GENERATED，勿手改`），再内联；开发态可直接打开源页面
- 内联顺序固定：rules → samples → knowledge → prompts → llm → pipeline → storage → file_parser → app
- 第三方解析器：PDF.js 主模块与 worker 以 base64 写入 `<script type="text/plain">`，运行时经 Blob URL 动态 import；Mammoth UMD 源码直接内联
- CSP：`script-src 'unsafe-inline' blob:`、`worker-src 'self' blob:`，只允许本地生成的 Blob，不放外部域名
- 输出 `dist/index.html`，体积必须 < 4 MB（当前实测约 3.1 MB）
- 构建后自动跑产物检查（含 PDF / DOCX 解析器与 `WB.parseFile` 是否内联）

## 4. 审查流水线

```
① 抽取 ──→ ② 法条 ──→ ③ 评估 ──→ ④ 复核 ──→ ⑤ 报告
   LLM       本地        LLM        本地+LLM      本地
```

| 步 | 输入 | 输出 | 实现 | 预算 |
|---|---|---|---|---|
| ① 抽取 | 合同全文（可能已脱敏） | `clauses[]`：`{index, title, text}` | LLM，JSON | ≤ 20s |
| ② 法条 | `clauses[]` + 合同类型 | `matchedRules[]` + `regSnippets[]` | 本地：规则关键词命中 + 法规库 BM25 top-k | < 1s |
| ③ 评估 | 条款 + 候选规则 + 法条片段 | `findings[]` + `lowRiskClauses[]` + `summary` | LLM，JSON | ≤ 45s |
| ④ 复核 | 全部中间结果 | `{passed, issues[], 修正后的 findings}` | 本地校验 + 轻量 LLM；error 自动重评 1 轮 | ≤ 15s |
| ⑤ 报告 | findings / lowRisk / summary | 六段式报告 HTML | 本地模板 | < 1s |

### 步 ① 抽取

- 输出：
  ```json
  { "clauses": [ { "index": 1, "title": "第一条 房屋基本情况", "text": "逐字原文" } ] }
  ```
- `max_tokens: 3000`（吸取 CLAUDE.md 中 2048 截断的教训）
- 要求逐字提取，不得改写；条款序号按出现顺序

### 步 ② 法条（纯本地）

- 规则筛选：`RULES.filter(r => r.enabled && (r.contractType === type || r.contractType === "通用"))`，再用 `r.keywords` 对条款原文做命中
- 法规检索：把 `regulation.json` 的 25 个主题文本切成段落，建立倒排索引，按规则关键词做 BM25 排序；条款 >18 条时 top-4，否则 top-8
- 检索结果同时记录 `ruleIds`，报告阶段反查回每条 finding，渲染为可展开的法条参考
- 输出给 LLM 的上下文只含命中的规则与法条片段，**不塞全量法规库**

### 步 ③ 评估

- 输出：
  ```json
  {
    "findings": [{
      "rule_id": "r_lease_penalty",
      "clause_index": 7,
      "clause_text": "逐字原文",
      "fairness": 4, "clarity": 3, "exposure": 5,
      "risk_reason": "……",
      "basis": "民法典第 585 条",
      "suggestion": "……"
    }],
    "lowRiskClauses": [ { "clause_index": 2, "clause_text": "……", "reason": "……" } ],
    "summary": "一句话总结合同整体风险"
  }
  ```
- 三维评分 0–5（5 最差），沿用 `prompts.py` 锚点
- **等级不在 LLM 输出中**：本地按确定性规则计算（见 §8）
- 覆盖要求：每条抽取出的条款必须出现在 `findings` 或 `lowRiskClauses` 中

### 步 ④ 复核

本地校验（全部确定性）：

1. 覆盖率：`clauses` 中每条都在 `findings` 或 `lowRiskClauses`
2. 等级映射：按三维分数重算等级，不信任 LLM 自报
3. 去重：同一 `clause_text` 只保留最高等级
4. 法条：`basis` 必须非空且匹配 `/第[一二三四五六七八九十百千\d]+条/`
5. 取值范围：三维分数为 0–5 整数

轻量 LLM 复核（`max_tokens: 800`）：只检查语义层面的漏判/误判，输出 `{passed, issues[]}`。
若存在 `severity: "error"` 且本轮未重评过 → 带 issues 重跑一次步 ③，最多 1 轮，然后无论结果如何继续。

- **长合同时间预算**：步 ③ 结束时已用 > 35 秒时跳过轻量 LLM 复核，只跑本地确定性校验，保住 90 秒上限；步 ④ 进度显示「长合同跳过 LLM 复核」
- **索引纠正**：`findings` / `lowRiskClauses` 的 `clause_index` 先用原文匹配回条款，模型写错一位时自动纠正，再做覆盖率与去重

### 步 ⑤ 报告

- 纯本地模板渲染，**不让 LLM 排版**
- 六段：总体概览 / 高风险详解 / 中风险条款 / 低风险条款 / 修改优先级 / 签约建议
- 每段内容来自结构化数据，格式永不漂移
- 每条风险可展开「法条参考」：本地检索命中的法规原文摘要，屏幕与导出都保留；屏幕端为 `<details>` 折叠，打印时隐藏以免报告过长

## 5. 规则数据化（架构红线）

### Schema

```json
{
  "id": "r_lease_deposit",
  "contractType": "房屋租赁合同",
  "name": "押金条款",
  "keywords": ["押金", "保证金"],
  "condition": "押金超过 2 个月租金或未约定退还期限",
  "level": "高",
  "basis": "民法典第 703 条",
  "advice": "建议押金不超过两个月租金，并写明退还期限",
  "enabled": true,
  "builtin": true,
  "stance": null
}
```

| 字段 | 约定 |
|---|---|
| `contractType` | 六类之一，或 `"通用"` |
| `level` | `高 / 中 / 低`，规则的默认严重度（用于条款库展示与 LLM 缺失时的兜底） |
| `basis` | 必须含具体法条编号；空值规则进不了构建 |
| `stance` | 规则级预留字段，MVP 恒为 `null`；2026-11-24 的审查视角是独立 `WB.STANCES`，不写回规则 |
| `builtin` | 内置规则 `true`，可停用不可删（V1.5 规则页可改可停用） |

### 内容量

- 房屋租赁 18 + 劳动 20 + 买卖 15 + 服务 17 + 合作 16 + 借款 14 + 通用 11 = **111 条**
- 2026-11-24 P0 + P1 扩容 45 条，补齐消保法及实施条例、公司法、合伙企业法、专利法、商标法、反不正当竞争法、仲裁法等此前空白；P2 暂缓
- 来源：`prompts.py` 的风险判定要求、`agent_langgraph.py:460` 的 `_REGULATION_CHECKLIST`、`knowledge/regulation.json`
- 每条必须带真实法条；雪玲整理，Nakko 抽查
- 2026-11-24 按中国政府网、最高人民法院、人力资源和社会保障部等官方渠道现行有效文本逐条复核，修正 6 处条文号；`WB.RULES_META` 记录核对日期与 20 部法规 / 司法解释版本。规则是离线预筛，法规修订后需重新核对
- 关键词先命中，命中后才交给 LLM 判断（省钱、可控）

### 规则拼装

- `WB.buildEvalPrompt({ contractType, clauses, matchedRules, regSnippets })`
- V1.5 加规则编辑器时只读写 `RULES` 数组，**不改审查链路**

## 6. 数据与存储

### IndexedDB

- DB：`contract-workbench`，version 3
- `settings`（key-value）：
  `provider` / `baseUrl` / `model` / `apiKey:<provider>` / `masking` / `hiddenNames` / `contractType` / `stance`
- `current`（单槽）：`{ contractText, contractType, stance, result, savedAt, reviewId }`，刷新后恢复；下一次审查覆盖
- `reviews`（keyPath `id`）：`{ id, createdAt, contractType, stance, title, contractText, result }`，按时间倒序展示；首页搜索覆盖标题/类型/原文；删除单条或清空
- `ledger`（keyPath `id`，index `endDate`）：`{ id, createdAt, updatedAt, title, contractType, counterparty, amount, startDate, endDate, paymentDate, paymentAmount, status, note, reviewId }`
- 历史 / 台账不可用时回退 localStorage；原文预览固定脱敏（证件/手机/银行卡/邮箱），完整原文仅本地保存

### 脱敏（默认开启）

- 发送前替换为占位符，返回后本地换回：
  | 类型 | 规则 | 占位符 |
  |---|---|---|
  | 身份证 | `\d{17}[\dXx]` | `【证件N】` |
  | 手机号 | `1[3-9]\d{9}` | `【手机N】` |
  | 银行卡 | `\d{16,19}`（在身份证之后匹配） | `【账号N】` |
  | 邮箱 | 标准邮箱正则 | `【邮箱N】` |
  | 公司名/人名 | 用户设置里的 `hiddenNames` 精确匹配 | `【主体N】` |
- 提示词中明确要求：**占位符必须原样保留，不得改写**
- 还原顺序：对 LLM 返回的 `clause_text` / `risk_reason` / `suggestion` / `summary` 做反向替换
- 本地规则匹配与正文高亮使用**原文**，不受脱敏影响
- 还原失败的占位符原样展示，不阻断流程

### 导出

- 报告 → `.docx`（真 Office Open XML：ZIP 内 `word/document.xml` 用 altChunk 引入表格化 HTML），文件名 `合同审查报告-YYYYMMDD.docx`；Word 桌面端打开无扩展名警告
- 台账 → `.csv`（带 BOM；`= + - @` 开头按文本处理，防公式注入）
- 到期 / 付款 → `.ics`（含 VALARM：到期提前 7 天、付款提前 1 天）
- 打印：`window.print()`，专用 `@media print` 样式；不做设置导出

## 7. LLM 接口

### 预设

| 名称 | baseURL | 默认模型 | 状态 |
|---|---|---|---|
| DashScope | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen3.8-max-0902` | ✅ 默认 |
| DeepSeek | `https://api.deepseek.com` | `deepseek-flash` | ✅ |

- 模型名可编辑，预设只是默认值
- 每家 Key 分开存；切换服务商不丢 Key

### 请求

- OpenAI 兼容 `/chat/completions`
- `temperature: 0`
- 非流式
- DashScope `qwen3.8-max-0902` 固定传 `enable_thinking: false`：默认思考模式会生成大量 reasoning，4000 token 被占满且单步超过 90 秒
- 尝试 `response_format: { "type": "json_object" }`；若服务商报错则去掉该字段重试
- 每步 `max_tokens`：抽取 3000 / 评估 4000 / 复核 800
- 超时：单次 120s；网络错误自动重试 1 次（指数退避 1s / 2s）

### JSON 兜底

1. 优先 JSON mode
2. 失败 → `WB.repairJSON()`（移植 `utils.repair_json`：去围栏、修尾逗号、单引号、前后说明文字）
3. 连续 3 次非法 JSON → 该步降级：显示原始文本 + "结构化解析失败，请重试或换模型"，不伪造报告

### 错误分类

| 情况 | 提示 |
|---|---|
| 401 / 403 | "API Key 无效，请到设置检查" |
| 429 | "请求太频繁，稍后再试" |
| 网络失败 | "连接不上服务商，检查网络或代理" |
| 超时 | "响应超时，可重跑该步" |
| 无 Key | 自动打开设置 |

## 8. 评分与报告

### 等级映射（确定性，照搬法眼）

- 任一维度 ≥ 4 → **高**
- 任一维度 = 3 且无维度 ≥ 4 → **中**
- 三维度均 ≤ 2 → **低**

### 综合评分（本地计算）

```
score = min(100, high × 15 + mid × 6 + low × 1)
```

越高风险越大。示例：3 高 + 5 中 + 2 低 = 77。
（实测后可微调权重，但必须在文档中留痕。）

### 修改优先级

高 → P0 必须改；中 → P1 建议改；低 → P2 可接受。

### 签约建议

- 高 ≥ 3 条 → ❌ 不建议签
- 高 1–2 条 → ⚠️ 修改后签
- 高 0 条 → ✅ 可签（有中风险时附"留意"提示）

### 报告免责声明

报告页脚与导出文件固定包含：
> 本工具输出为 AI 辅助结果，不构成法律意见。正式签署前请由执业律师复核。

## 10. 错误处理与边界

| 情况 | 行为 |
|---|---|
| 输入为空 / 少于 50 字 | 阻止并提示 |
| 超过 3 万字 | 提示"合同较长，审查可能变慢" |
| 超过 5 万字 | 硬上限，阻止提交 |
| 上传扫描版 PDF / 加密 PDF / 损坏文件 | 明确提示原因；扫描版建议粘贴文字或换 DOCX，不静默失败 |
| 上传旧版 `.doc` | 提示另存为 `.docx`，不尝试解析 |
| 上传文件超过 25MB / PDF 超过 300 页 | 解析前阻止并提示上限 |
| 解析后超过 20 万字 | 拒绝并提示拆分，不截断后偷偷送审 |
| 解析后超过 5 万字但不足 20 万字 | 填入文本框并标红提示；开始审查时按 5 万字硬上限阻止 |
| 解析中再次点击审查 | 阻止提交，提示等文件解析完成 |
| 解析超过 60 秒 | 超时提示检查文件或拆分，不把界面永久卡在「正在解析」 |
| 审查中刷新/关闭 | `beforeunload` 确认提示 |
| 重跑某步 | 保留已完成步骤的中间结果，从失败步继续 |
| 关闭脱敏 | 原文直发；设置里明确说明后果 |
| 无网络 | 界面/条款库可用，审查按钮提示需要联网 |
| API Key 未配置 | 点击审查时自动打开设置 |
